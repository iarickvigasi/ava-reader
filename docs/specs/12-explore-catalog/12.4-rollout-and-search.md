# Explore · rollout and search scaling

> Status: draft · Updated: 2026-10-23 · Parent: [\_overview](_overview.md)

## Deployment and search

Browser → catalog gateway/CDN → Catalog API replicas → catalog PostgreSQL/projections.
Browser → main API → main PostgreSQL for personal actions and reading; neither Explore search nor
bulk catalog ingestion passes through the main API. Initially run web, APIs, workers, and both
PostgreSQL instances as separate containers/services on one server with independent resource limits.
Give each DB its own credentials, data volume, connection pool, and off-host backup/restore process.
Use configurable service URLs and DB hosts, never shared database tables or local file assumptions.
Shared hardware still permits contention and a host outage affects everything. Monitor CPU, RAM,
disk latency, free space, and reading latency; throttle imports before they impair reading.
Move services/DBs to separate hosts as load grows: restore/replicate data, briefly pause writes for
cutover, change endpoints, and verify links/queues. No domain-model rewrite should be required.
Catalog primary writes come from controlled ingestion/admin workers; API reads use bounded pools.
Public pages use ETag/revisions and short cache lifetimes; avoid caching personalized main responses.
Rate-limit and debounce search; cap query length/page size, apply statement timeouts, and use cursor
pagination for ordered lists. Ranked search needs stable score+ID cursors or bounded pages.
Do not permit unlimited deep result scans/counts. Keep exact ISBN lookup separate from fuzzy search.

PostgreSQL is the initial search candidate: GIN text search plus pg_trgm for short titles/aliases.
Prioritize exact identifiers, exact/alternate titles, author/title matches, then fuzzy candidates.
Work-grouped results avoid edition spam; edition filters must match the same edition (e.g. language
and format), not independent arrays that imply a nonexistent combination. Fetch relevant editions.
Cache hot public details and queries only after observing reuse; Redis is optional, not day-one.
Read replicas can isolate catalog reads from imports, with explicit replication-lag monitoring.

| Search option           | When to choose                                                                          |
| ----------------------- | --------------------------------------------------------------------------------------- |
| PostgreSQL              | Lean baseline if relevance/latency pass at the intended launch corpus and traffic.      |
| Typesense / Meilisearch | Evaluate when typo tolerance, facets, or query load justify another service.            |
| OpenSearch              | Evaluate for more complex analyzers or corpus/sharding needs; higher operational scope. |

Dedicated search is a derived store, never authority. Outbox consumers perform revision-aware upserts
and deletes, retry safely, and rebuild from a canonical snapshot plus subsequent events. Swap index
aliases only after catching up; reject old revisions so delayed jobs cannot resurrect deleted data.
[Typesense production guidance](https://typesense.org/docs/guide/running-in-production.html) documents
HA, memory planning, and alias swaps; benchmark actual AVA documents before choosing sizing/vendor.
If dedicated search fails, use cached results/detail lookup and bounded fallback, not unlimited SQL.

Foundation implemented in [12.5](12.5-foundation.md); production operations and later phases remain.

## Implementation sequence

1. Accept/revise ADR; settle user-shelf/copy semantics and baseline traffic/budget assumptions.
2. Create catalog service/schema/migrations and separate instance on the initial shared server; add
   private networking, credentials, backups/PITR, restore drill, metrics, and catalog reads/lookup.
3. Build minimal dump importer with provenance, redirects, checkpoints, and outbox. Load a sample,
   benchmark, then grow to intended launch coverage. Scrapers can use this adapter contract later.
4. Implement bounded search and multilingual relevance fixtures; select search engine from evidence.
5. Backfill only existing shared catalog books to canonical works/editions with legacy-ID mappings.
   Keep private imports unmatched until ownership-safe linking; preserve all content identities.
6. Add saved-work tables/bucket queues, generalize collection membership, and upload attachment.
   Backfill personal links incrementally; enable via feature flag and validate before cutover.
7. Switch Explore/admin metadata ownership; retain legacy mapping for existing catalog additions.
   Migrate approved public assets separately; retire old catalog routes only after link verification.

## Validation and sizing gates

Proposed targets, not measurements: search p95 <300ms at gateway, detail p95 <200ms, projection lag
<60s for ordinary edits. Define expected launch QPS, test at 2× peak while ingestion runs, and test
10× corpus growth; derive CPU/RAM/storage from sample expansion and index measurements, not dump size.
Track zero-result rate and correct top-5 results on curated multilingual queries, including ISBNs,
typos, pen names, same-title works, translations, and new releases. Measure each language separately.
Test replay/older revisions, ambiguous ISBNs, merge/split correction, source deletion, outage, private
upload isolation, duplicate offline saves, and pending mutations through merge/account-switch.
Exercise shared-host contention limits, cross-host cutover, index rebuild, backup restore, and rollback. Rollback keeps new personal rows/queues readable;
never undo a migration by deleting saved works. No production implementation or load testing occurred.
