## Summary

Keeps account access available online, offline and during loading, and caches profile photos so they
render from Dexie instead of Clerk's own (network-dependent) `<UserButton>` image when offline.

## Scope

- In: the avatar slot in the app-shell header (mobile + desktop bars); caching the photo bytes; an
  initials fallback.
- Non-goals: account management without connectivity.

## Behaviour

1. Show the cached/network photo when available; otherwise use the user's initial. Loading and
   offline failure must not remove account access or expose a broken image.
2. `UserMenuButton` uses an app-owned, keyboard-accessible menu, available even when Clerk fails to
   initialize. It always retains the same cached-avatar component rather than swapping it out.
3. Explicit sign-out works locally while offline, warns about unsynced changes, and retries server
   revocation on reconnect ([[7-auth]]). Manage account is available when Clerk is loaded; otherwise
   the menu offers sign-in. Session expiry never removes the cached avatar or books.
4. Outside clicks/taps and pathname changes (including Back/Forward) close the account menu without
   blocking the outside control. Escape closes it and returns focus to the avatar. Manage account
   closes the menu before opening the profile. Inside interaction and avatar toggling still work.
5. Name and avatar activate the same keyboard-accessible account menu. Long names remain available
   without blocking other header actions. Mobile retains account-menu access.

## Data & sync

Extends the `me` bucket (single-row, `apps/web/features/offline/buckets/me`): `CurrentUserRow` gains
`avatarBlob: Blob | null`, cache-first + lazy-write-through; cover bytes use a separate store
(ADR 9) ([[4.1-offline-reading]]) — `readAvatarBlob`/`useAvatarBlobUrl` check Dexie first; a cache
miss with a network `avatarUrl` present triggers `persistAvatarFromNetwork` in the background.
`applyCurrentUser` preserves the existing `avatarBlob` across re-applies with the same photo URL (an
online reload must not silently wipe the cached photo). No new table/index, so no schema version
bump.

## Edge cases

No `avatarUrl` (Clerk `hasImage` false) → initials only, no fetch ever attempted. A changed or
removed photo URL invalidates old bytes. Fetch fails (offline/CORS) → swallowed, retried next mount
or reconnect, no backoff. iOS 7-day storage wipe ([[4.1-offline-reading]]) applies the same as cover
blobs — refetched lazily next time online. Sign-out/account switch deletes the whole per-user
database ([[4.7-data-isolation]]), so the cached avatar goes with it.

## Acceptance criteria

- [ ] Account-menu access remains available while the avatar loads or fails offline.
- [ ] A previously-viewed profile photo renders from cache when opening the app offline.
- [ ] A user with no photo (or never-cached photo, offline on first-ever load) sees their initial as
      a fallback, never a blank space or broken-image icon.
- [ ] An online reload never drops a previously cached avatar photo.
- [ ] Desktop and mobile menus dismiss on outside interaction, pathname changes, and Escape; Manage
      account closes the menu before opening the profile, including after offline use.
- [ ] The whole desktop chip toggles the menu, highlights on hover in both themes, and supports
      keyboard activation with a visible focus ring.
- [ ] Short names produce shorter chips; long and unbroken names remain fully visible without
      ellipsis, clipping, or header overflow.

## Open questions

None.

## Avatar reliability update

- Current-user photos share a reactive cache across the header, Connect preview and own reader card.
- Initials stay visible until an image loads successfully, including slow/offline and failed loads.
- Cache writes notify mounted avatars; duplicate concurrent downloads are coalesced.
- Cached current-user photos render through in-memory data URLs, without revocable blob URLs.
  Superseded reads are cancelled; metadata refreshes never leave an expired URL on a mounted image.
