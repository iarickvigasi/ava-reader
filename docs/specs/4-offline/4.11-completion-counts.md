## Rule
A book is completed when its user's `LibraryItem.finishedAt` is non-null **or** its reading
progress is at least 100%. Both conditions together still contribute one completion. Removing a
date makes a book unread only when progress is below 100%. Saving or removing a date never
changes percentage, reading position, reading time, or activity timestamps.

Collection unread counts apply this rule to their active members. Home's Books Read count covers
all of the user's library items, including archived items. Collection membership and offline-save
membership affect the corresponding shelf, not the home-wide completed-book total.

## Complete snapshots with a partial book cache
Each collection aggregate carries a lightweight `completionItems` array containing every member's
libraryItemId, finishedAt, and completionPercent. Home carries the same data for every item counted
by its stats and a separate array for each collection summary. These arrays are complete even when
the response includes only a four-book preview or the browser has cached only one book's details.
Cached preview rows and the local progress table must never replace a whole-library total.

An absent array means a legacy snapshot with unknown per-item contributions. Its server counts
remain valid until revalidation supplies completion metadata. An empty array is a known empty
snapshot. Home retains its previous library-membership fallback only for old collection summaries
without completion metadata.

## Reconciliation
The per-user database stores a monotonic completion revision in `meta`. Local completion-related
writes and acknowledgments advance it in the same transaction as their state change. Aggregate
requests capture the revision before fetching, and their apply transaction rejects the response
if the revision changed or the active account switched. This also covers changes from another tab.

Each cached aggregate retains its own request-start revision. Acknowledged date, progress, and
membership fields retain independent revisions, so saving a date cannot freeze an older progress
value. Reads overlay acknowledged fields newer than that aggregate and then pending local edits;
a pending or acknowledged null is an explicit date removal. Clearing the mutation queue does not
discard an adjustment still needed by an older aggregate. Refreshing one collection does not
change the home snapshot's revision.

Read the aggregate, field overrides, and pending edits in one Dexie transaction. Otherwise a read
could combine the old server fields with a queue that an acknowledgment has just emptied. Evaluate
completion and membership together: finishing a book and removing it from a shelf must change its
contribution only once.

RSC and cache-loader payloads do not have a trustworthy local request-start revision. They seed
missing cache entries and do not overwrite an existing home snapshot. Composed counts are read
results; never write them back as the raw server baseline or add completion deltas to them again.

## Acceptance criteria
- [ ] Manual date, progress at 100%, and both together each count the same book once.
- [ ] Clearing a date below 100% removes one completion; clearing it at 100% removes none.
- [ ] Counts include uncached snapshot members and home-only archived items.
- [ ] Pending finish, membership, and offline-save edits compose without double subtraction.
- [ ] Acknowledgment, reload, and refresh of another aggregate do not make local counts regress.
- [ ] Older GET responses cannot overwrite an acknowledged edit from this or another tab.
- [ ] Home stats and collection summaries update from live cache reads online and offline.
