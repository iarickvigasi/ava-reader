# Reader · payload & package (server)

> Status: shipped · Updated: 2026-08-11 · Parent: [[_overview]] · Code:
> apps/api/src/reader/{reader-payload.ts,package/}

## Summary
The server side of opening a book: resolves the owned library item, decides whether the reader can
render it, and returns a **ReaderStatusPayload** — book metadata, a small window of chapters, the
TOC, and the resume position. Everything the client specs (1.1–1.6) consume starts here.

## Scope
- In: the four payload statuses, chapter-window selection, the stored reader-package format and its
  legacy normalization, the in-process package cache.
- Non-goals: producing the package (that is the processing pipeline, see
  [[18-chapter-purpose-analysis]] for the analysis that annotates it), progress maths and sessions
  (see [[5-reading-sessions-progress]]), all client rendering (1.1–1.6).

## Behaviour
`GET /reader/:libraryItemId?chapterId=` returns exactly one of four statuses. Every status carries
`book` and `progress`, so the client can show the title and resume position even when it cannot
render:

1. **UNSUPPORTED** — no primary `SOURCE` file, or its format is not supported. Terminal for that item.
2. **FAILED** — no ready `DERIVED_READER` file and the latest processing run failed. Message is the
   run's `errorMessage`, falling back to a generic line.
3. **PROCESSING** — no ready `DERIVED_READER` file and no failed run: the package is still building.
   The client polls.
4. **READY** — adds `activeChapterId`, `chapters` (the window), and `toc`.

Opening a READY book also fires chapter-purpose analysis lazily, unawaited and error-swallowing, so
a bulk import costs nothing and only books actually opened are paid for ([[18-chapter-purpose-analysis]]).

**Active chapter** resolves in order: the requested `chapterId` → the resume locator's chapter →
the first chapter. A package with zero chapters is a 400.

**Chapter window.** Only the active chapter ±1 is sent, never the whole book — a full package is
tens of MB parsed. This bounds the response and is what 1.3's prev/next traversal pages through.

## Data & sync
**Stored reader package** (`StoredBlob`, referenced by the `DERIVED_READER` `BookFile.blobId`) is
JSON with a `version` and `chapters`. Any other shape is a 400.

- **v2** — current. `toc` is a tree of `ReaderTocNode`; `manifest.authors` is an array.
- **v1** — legacy, normalized on read: the flat `toc` array becomes single-level nodes with
  synthetic `toc:<i>` ids and empty `children`; `manifest.author` (string) becomes `authors`.

Both versions then get XML entities decoded across chapter labels/titles, manifest title/authors,
and TOC labels, so `&amp;` never reaches the UI. `parseReaderPackage` is the single entry point —
book-analysis reads through it too, rather than growing a second parser that could drift.

**In-process package cache.** Parsed packages are held in a 4-entry LRU keyed by `blobId`, which is
immutable (regenerating a package writes a new `StoredBlob`), so the key never goes stale. Without
it every chapter navigation re-reads a multi-MB blob from Postgres and re-parses it, spiking memory
and risking an OOM kill. Concurrent loads of the same `blobId` are coalesced into one parse.

## Edge cases
Non-EPUB or missing source → UNSUPPORTED; processing never finished → PROCESSING indefinitely (the
client keeps polling); package present but chapter-less → 400; requested `chapterId` absent from the
package → falls through to the resume chapter, then to the first; active chapter at either end of
the book → the window is truncated, not padded.

## Acceptance criteria
- [ ] A non-EPUB item returns UNSUPPORTED with book metadata and progress still populated.
- [ ] A failed processing run surfaces its own error message, not a generic one.
- [ ] A v1 package renders identically to v2, with a usable TOC and author list.
- [ ] Repeated chapter navigation on one book parses the package at most once.
- [ ] Encoded entities in titles, chapter labels and TOC labels reach the client decoded.

## Open questions
Whether the window should widen on fast sequential navigation; eviction policy under many
concurrently-open books (4 entries is a guess, not a measurement).
