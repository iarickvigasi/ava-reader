## Summary
Turns a raw DOM text selection into a structured, anchored intent that the highlight and AI overlays
can act on.

## Scope
- In: capturing the active selection, holding it in context, deriving a range locator from it,
  exposing it to highlight and AI-toolbox overlays.
- Non-goals: persisting highlights (see 2-highlights), generating AI output (see 3-ai-toolbox /
  4-ai-comments), locator internals (see 1.4-locators).

## Behaviour
1. use-reader-text-selection observes the browser Selection and normalizes it to a reader range
   (chapter, blocks, offsets, text).
2. reader-selection-context publishes the current selection so overlays render relative to it.
3. compute-ai-comment-locator derives a ReaderRangeLocator (with contextBefore/After) from the
   selection for AI tools.
4. use-highlight-selection-bridge converts the selection into a highlight intent (excerpt + locator)
   for the highlights bucket.
5. Selection clears on dismiss, navigation, or empty re-select.
6. On touch, selecting and page-swiping are mutually exclusive: while a non-empty selection is
   active inside the reader, the swipe handler suppresses page navigation
   (resolveSwipeNavigationOutcome), so extending or adjusting a selection never turns the page. This
   is touch-only — desktop selection uses mouse events, which have no swipe path.

## Data & sync
No persistence of its own; produces ReaderRangeLocator (spec 4) consumed by highlights and
ai-comments buckets. Pure client state via context.

## Edge cases
Empty/collapsed selection; selection spanning blocks or chapters; selection over an image; selection
lost on reflow/resize; touch vs mouse selection; a touch selection-drag whose horizontal travel
exceeds the swipe threshold must select, not page (mobile-only — the collision that caused
wrong-fragment / opposite-direction selections and a silently turned page behind the panel).

## Capture invariants (keep these true)
Touch capture is fragile because browsers fire a *storm* of events per gesture and differ across iOS
/ Android. Keep these to avoid the wrong-fragment / double-open / callout-over-panel regressions this
file keeps hitting (see [[glossary]] for terms):
- **One check per gesture.** Every capture path goes through the *settle scheduler*'s single slot —
  never read `window.getSelection()` directly from a handler, or the burst one gesture emits
  (`touchend` then a synthetic `mouseup`) re-opens the panel twice.
- **Gate every read on container containment:** the event target must be inside the page box.
  `touchend` reports the node the finger went down on, so this also keeps a tap on the
  panel/backdrop from being read as a selection.
- **Touch checks drop the live selection** (`removeAllRanges`) so the *native callout* stays off the
  panel; **mouse checks keep it** (desktop has no callout). This is the only difference between the
  two check kinds — schedule them through separately named paths, not one flag.
- **Tune delays in `selection/capture/timing.ts`,** never inline — today only
  `IMMEDIATE_SETTLE_MS`.
- **Known gap:** a *compatibility (synthetic) mouse event* echoing a real touch selection lands in
  the scheduler's single slot after that gesture's touch check and re-reads it with the mouse rules,
  so the live selection is not dropped. A touch check must win over a synthetic echo for the same
  gesture; unverified on device.

## Acceptance criteria
- [ ] A text selection yields a correct range locator with usable context fallback.
- [ ] Both highlight and AI overlays anchor to the same selection.
- [ ] Selection clears on navigation/dismiss without leaking stale state.
- [ ] On touch, extending or adjusting a selection never turns the page; a swipe with no active
      selection still navigates.

## Open questions
Multi-range selections; selection persistence across page turns.
