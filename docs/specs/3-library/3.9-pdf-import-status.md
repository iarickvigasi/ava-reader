# 3.9 PDF import status and formats

Code: `library/pdf-import/` (API), `features/offline/buckets/library/pdf-imports/`
and `components/app/shared/pdf-import/` (web).

## Outcome and fixed behavior

Upload a PDF, select **Convert to EPUB**, and receive one finished readable book in the Library.
Conversion happens once during import. Finished content stays fixed; there is no later conversion
or replacement. English one-/two-column prose is qualified internally, not explained beside the
checkbox. AVA pays for processing; no prices, credits or token controls appear.

After durable acceptance, the same Library entry shows Queued, Processing, Needs check, Ready or
Failed. Original PDF belongs to that entry and is downloadable through its owned route. Read and
EPUB require actual accepted publication. Internal reader JSON is never a format choice. Failed
remains visible with a diagnostic reference and recorded investigation; no reader Retry/Cancel.

## Import and observation

- EPUB import retains the existing path. PDF selection opens a minimal confirmation with the file
  name and Convert to EPUB. The current prototype's unchecked, required conversion choice remains
  the implementation draft while its default/unchecked policy awaits founder response.
- Persist a per-account request identity before upload; uncertain transport cannot imply failure or
  start a new conversion. Reconcile by that key, or replay the same file/key. A duplicate source
  opens its existing Library entry; no implicit extra copy.
- All persisted status and upload intent live in the Library bucket. Never store PDF bytes in the
  intent record. Observe only while online and visible, with bounded backoff and auth fencing.
- Account/database changes, deletion and an older operation generation/timestamp cannot overwrite
  current data. Ready/Failed are terminal; stale lists cannot erase status or a final content ID.
- Offline shows cached last-known status, never simulated progress. Server failure or auth loss
  retains the saved entry. A measured stage count may be shown; no fabricated total percentage/ETA.
- Metadata edits use the existing versioned API; polling cannot overwrite edited fields.

## Notifications and privacy

The draft in-app notice links to the same Library item and acknowledges a durable terminal intent;
status persists after dismissal. No email/push sending is enabled. Exact channel selection remains
pending; required failure recording and visibility are fixed. Delivery and acknowledgment never
clear immutable failure/publication facts. Source bytes, cover, EPUB and resources stay owner-only.

## Acceptance / evidence

- [ ] PDF confirmation creates one accepted entry; lost response/reload reuses its request identity.
- [ ] Library and details agree, including cached offline state and terminal Failed.
- [ ] No premature Read/EPUB or internal JSON format; owned source download works before/after failure.
- [ ] Status cannot regress, resurrect deleted entries or cross accounts; metadata edits survive.
- [ ] Terminal notification is durable and deduplicated, without Retry/Cancel or user spending UI.
- [ ] Real narrow/wide keyboard and assistive controls pass; actual import-to-reader flow is verified.

Automated checks, stub completion and real conversion journeys are reported separately. Integration
uses 3.4 import, 3.6 jobs, 3.7 providers and 3.8 publication; no UI timer can certify the reader.
