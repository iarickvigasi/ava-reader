## Summary

Server ingest: POST /library/import turns an uploaded EPUB/PDF into a Book with stored files and
a LibraryItem on the user's shelf. Adding from the catalog reuses the same add-to-library core.

## Behaviour

1. Only EPUB and PDF are accepted (server-side format detection); anything else 400s.
2. Metadata (title, authors, description, genres, language, published year, cover image) is
   extracted server-side; the source file and cover are stored as blobs. EPUB subjects split on
   commas and spaced hyphens/double hyphens; genres are trimmed, nonempty, and deduplicated in order.
3. Blob bytes are written before the metadata transaction — multi-MB writes would blow the
   interactive-transaction timeout and hold row locks for the whole upload. If the transaction
   fails, the blobs are best-effort deleted; leftovers are swept by the orphan-blob GC.
4. An ordinary external EPUB enqueues a normalize-reader-package-v1 processing run
   ([[2-reader/2.7-reader-payload]]); a PDF stores the source only.
5. Add-to-library is idempotent per user+book: an existing item returns state "existing" (and
   backfills originCatalogEntryId when newly known); otherwise the item is created with a unique
   per-user slug built from title+authors, a zeroed ReadingProgress, and smart-shelf membership
   ([[3.3-collections]]). Response: LibraryMutationPayload {state: added | existing, book, slug}.
6. Catalog adds flow through the same core with source CATALOG and the originating catalog entry
   recorded; only PUBLISHED entries can be added.
7. Client side, a successful upload revalidates the library bucket and refreshes the router, and
   the status message it shows must not displace the import button ([[3.1-library-screen]]).

## Ordinary EPUB chapter labels

Keep usable TOC labels under the existing TOC trust rule, then explicit opening headings regardless
of book-wide title coverage.
For adjacent number and descriptive headings, use the descriptive title; a lone number remains
usable. Ignore images/empty blocks before the opening, and never promote later subsection headings.
Short opening paragraph guesses retain the existing coverage safeguard against stray dialogue.
Otherwise use the final chapter order plus up to six words from the first body sentence:
`1. It was a bright cold day…`.
Skip headings, images, and empty blocks; normalize whitespace and replace trailing punctuation with
`…`, even for short sentences. Use language-aware sentence and word segmentation. Without body
text, use only `1.`. Chapter labels, fallback titles, and fallback TOC entries agree. This applies
to newly generated packages. A maintenance backfill can replace legacy `Chapter N` labels in
stored packages without reparsing content. It also upgrades exact generated excerpts (including
number-only fallbacks) when opening headings supply a title. Authored names remain unchanged;
the device label refresh updates legacy downloads on reconnect ([[4-offline/4.1-offline-reading]]).
Accepted canonical PDF/generated-EPUB content is immutable and excluded from this maintenance path.

## Edge cases

Ordinary `/library/import` uploads create a new Book and LibraryItem, including repeat uploads.
Adding the same catalog Book again returns "existing". Failure before ordinary upload acceptance
leaves no visible book and no orphaned blobs (GC backstop); unsupported file → 400 before any write.
The conversion route has its own request/source deduplication. Once processing is accepted, failed
PDF conversions and generated-EPUB preparations retain their visible Failed entry and diagnostics.

## Acceptance criteria

- [ ] Importing an EPUB or PDF creates the book, its smart-shelf membership, and progress at 0.
- [ ] Ordinary `/library/import` reuploads create another Book and LibraryItem; selected PDF conversion follows its deduplication contract.
- [ ] Adding the same catalog Book again returns state "existing" and adds nothing.
- [ ] Untitled chapters use six-word opening excerpts with order numbers and a trailing `…`.
- [ ] Chapters without body text use only the order number and period; real titles are preserved.
- [ ] Sparse TOCs and untitled front matter never suppress an explicit opening chapter heading.
- [ ] Separate headings `1` and `Wanted: Men Who Love` yield `Wanted: Men Who Love`.
- [ ] Label repair preserves blocks, IDs, locators, nested authored TOC labels, and progress counts.

## Selected PDF conversion direction (not shipped)

Conversion is selected once at PDF import; finished content is fixed. English ordinary single/double
columns, AVA-funded processing, terminal Failed with diagnostics/notification/investigation are agreed.
The additive `POST /library/pdf-imports` backend accepts explicit conversion with an owner-scoped
Idempotency-Key. It durably stores one item/source/operation, replays that request, rejects mismatches
and new-key duplicates, and provides owned status/source/cover and conditional metadata endpoints.
See [owned upload decisions](../../adr/9-owned-pdf-imports.md) and [checks](../../pdf-import-checks.md).
The generated EPUB import extension below uses `/library/import`; ordinary external imports retain their existing path. Durable native background work is defined in [[3.6-pdf-jobs]]; publication and status
UI are implemented in the integration candidate. Signed-in desktop native and generated-EPUB reimport
flows passed under local TEST qualification; complete supported-book/device qualification remains open. See [[3.7-provider-ledger]], [[3.8-pdf-publication]] and [[3.9-pdf-import-status]]. In the selected design, one Library entry shows progress or Failed;
its details list the original PDF and, only after acceptance, the generated EPUB. Read readiness,
format downloads and device offline availability stay separate. Failed entries remain visible.
One identity holds the finished reading content, marks and progress; no manual format attachment,
edition merging or later conversion is implied. Checkbox defaults, intentional duplicate controls
and notification timing remain design work.

The conversion option copy is **Convert to EPUB** alone. Finished-content/profile/funding details
are not adjacent helper text; processing details remain secondary. Source scope and validation
remain enforced. The opt-in backend does not select checkbox defaults or deliberate-copy UI policy.

## Generated EPUB reimport (integration candidate)

An EPUB declaring AVA's generated profile is saved immediately as a new owned source/item and
queued for bounded, recoverable background preparation. It receives a new content identity;
portable owner/job/publication claims never become server authority. Malformed declared profiles
fail preparation without falling back to ordinary EPUB parsing.

The isolated validator checks exact visible XHTML, chapter files, navigation, styles, canonical
semantics and images, plus EPUBCheck. A successful result retains immutable reader/resource
bytes. It becomes readable only when an approved reader qualification covers all required
features; waiting for qualification never replaces the finished content. Owned image downloads,
positions and translations use this import's authority. A validated cover may appear through an
authenticated owned URL before reader qualification; showing a cover does not make Read ready.
See [ADR 13](../../adr/13-canonical-epub-import.md) and [scoped checks](../../pdf-content-checks.md).

- [ ] Reimport a generated EPUB through ordinary upload and preserve rich content in the reader.
- [ ] A repeat upload has its own source, owner/item scope and final content identity.
- [ ] Invalid declared content never produces a lossy legacy reader; ordinary EPUBs still work.
- [ ] Concurrent/restarted preparation cannot duplicate acceptance or expose another owner's bytes.

Source implementation and contract checks are separate from app/reader qualification evidence.
