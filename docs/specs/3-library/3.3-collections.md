## Summary
Collections group books into CUSTOM or SMART lists. SMART shelves are system-owned and derived;
CUSTOM lists are user-managed.

## Behaviour
1. Three SMART defaults — Imported Books, Public Domain, Offline Books
   ([[4.8-offline-books-collection]]) — are upserted (keyed by per-user smartKey) whenever a book
   is added to the library; their names/slugs resolve uniqueness against non-smart namesakes.
2. Adding a book joins it to the smart shelf matching its source (IMPORTED → Imported Books,
   CATALOG → Public Domain); membership upserts are idempotent. Offline Books membership mirrors
   offlineRequested in the same transaction ([[4.8-offline-books-collection]]).
3. Rename (PATCH /library/collections/:id) requires a non-empty name, normalizes the description
   (trim; empty → null; omitted → unchanged), 400s on a duplicate name, and is forbidden (403)
   for SMART shelves.
4. Delete (DELETE /library/collections/:id) is forbidden (403) for SMART shelves — they would be
   recreated on the next import and only flicker out and back.
5. Create (POST /library/collections) creates an owned CUSTOM collection with a unique slug and no books.
   Create and edit trim field edges and capitalize the first letter, preserving remaining text.
   Title is required (maximum 100 characters); description is optional (maximum 1,000; blank → null).
   Both reject case-insensitive duplicate titles within the user's collections. Serializable
   transactions retry concurrent write conflicts. Existing case-only duplicates are left unchanged.
   The UI reuses the localized edit form. Clicking New collection offline opens the existing offline
   dialog; losing connection in the form displays an inline message and preserves the draft.
   Successful creation updates the library cache; empty custom collections remain visible without books.
6. A collection page reads by id or slug ([[3.5-library-payloads]]).
7. PATCH /library/:libraryItemId/collections accepts addCollectionIds and removeCollectionIds.
   Both lists contain collection IDs; duplicates are harmless, overlap is invalid (400). Owned
   active book and owned collections are required (404 for absent or foreign records). SMART
   targets are rejected (403). Additions/removals are atomic and idempotent; unrelated memberships
   are preserved. The response includes complete book memberships and full affected collections.
8. Custom membership changes are local-first through the library bucket, persisted per user and
   retried on reconnect. Pending changes survive refreshes and older in-flight acknowledgments.
   Counts use server totals plus local changes, not preview length. Successful sync reconciles
   book details, affected shelves, and home summaries. Permanent failures are surfaced and reconciled.

## Edge cases
A book in multiple collections; a deleted collection leaves its books in the library; empty
collection states.

## Acceptance criteria
- [ ] Renaming/deleting a CUSTOM collection persists and survives reload.
- [ ] SMART shelves refuse rename and delete with a 403, in the UI and the API.
- [ ] Custom membership edits persist, are idempotent, and preserve SMART/unrelated memberships.
- [ ] Offline edits survive reload; previews, full shelves, and counts agree after synchronization.

## Open questions
Reordering collections has no endpoint yet.

## Known gaps / planned fixes
- Counts can mix snapshots. Return compact active member IDs and unread status alongside CUSTOM
  totals; cache these together, independently of preview cards and preserved display links. Derive
  pending deltas from this snapshot, removing timestamp guesses and queued membership baselines.
  Acknowledgments replace the snapshot and automatically rebase remaining edits. Legacy caches
  without membership evidence retain edits but defer count adjustments until a full snapshot arrives.
- Home counts can revert after successful sync. Patch affected cached home summaries in the same
  transaction that applies the acknowledgment and retires its queue entry. Preserve unrelated home
  data; seed only an empty cache, reject older in-flight home responses, and read home plus pending
  changes consistently. Refresh still owns changes to the home panel's ordering and included shelves.
- Verify newer book details versus older totals, preserved stale links after preview refreshes,
  off-preview books, multiple pending books, in-flight reversals, unread changes, and legacy caches.
  For home, verify a failed refresh after success, stale fetches/seeds, and unrelated data preservation.
- Cross-tab stale-response coordination is deferred; the above home response guard is per tab.
